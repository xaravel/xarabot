# Maintainer note: speed, tests and autonomy (2026-10-24)

**Status:** raw input, not decided. Ed recorded it while watching Xarabot's own lane build Epic 2, mid-Story 2.5b. It is meant for a later course correction of Xarabot and Xaravel, or a `bmad-forge-idea` session. It is not a plan, and nothing here changes what lanes do today.

## Themes, distilled

1. **Time over tokens.** When a test fails, the question is how far back to go to prove the test good, against letting the project move on. Ed's lean: time matters more than tokens. Not by loosening tests, but by **acknowledging a failure and moving on**, then looking ahead to find the first downstream place where that failure would actually matter, if anywhere. The risk he names: downstream work built on a real break gets wasted and has to be redone.
2. **"Flaky" needs a rule, not a label.** One failure means broken. "Flaky" has to be earned by a deterministic definition, for example passes on N of M reruns of the same commit, plus a known cause class such as timing or load. Without that rule, "flaky" becomes an excuse.
3. **Deterministic guards for agent mistakes.** Running this for a week shows a recurring class of agent errors: hallucinations, broken rules, jumped guardrails. A test, check or gate is the right defence, because it holds where instructions don't.
4. **Autonomy while the Maintainer is offline.** Agents should go ahead on best-case decisions, except for a protected class: changing tests, credentials, policy, and other classes to be defined. When Ed is back he gets a short catch-up: "here's what we decided in the last N minutes, the route we took, and which tests failed and how we treated them". The point is that most code never touches these one-off decisions, so pausing everything for them costs more than it saves. One goal is letting one person run several projects and agents without being pulled in all day and night.
5. **Planning vs pace.** BMAD's full planning plus a multi-agent harness works ("we're through Epic 1, mid Epic 2"), but it feels slow next to pure vibe coding. The aim is to keep the planning and safety while cutting the round-trips.
6. **Learning across projects.** Xaravel's loops and Xarabot's lanes show echoing patterns. Some lessons generalize: abstract them from Xaravel back into Xarabot. Some are specific to one repo. Some patterns only show up across many Xarabot projects, never in any single one, so there should be a way to watch for them. Ed links this to the idea of LLM "dreaming", where a model learns from its own recollections, such as journals, retros and lane logs.

## What today showed (evidence for the themes)

- **The flaky test.** `createGitMerger > fetches only the SHA runner.git lacks` failed under full-suite load, passed alone (3 of 3), and ejected PR #69 from the merge queue once. Its re-queue passed. Story 2.5c is now scoped to find and fix it. Themes 1 and 2.
- **Intent-gap stops.** Stories 2.4, 2.5 (three runs) and 2.6 each stopped `blocked` on a planning gap, and each needed a Maintainer round-trip. It was settled by the correct course in #67. Theme 4.
- **The standing rule.** "Merge green when okay" (2026-10-24) removed the per-PR round-trip for green, unflagged PRs, an early step toward theme 4.
- **Guardrails that held.** Sessions refused to decide C10 and other Maintainer questions. Auto mode refused unrequested approvals and merges, and refused creating a public repo. Theme 3.
- **Guardrails that were missing, each found by a review or a live run, not by a test:**
  - `expected_checks: [check]` made the lane ignore a failing `check`;
  - the write check's Unicode fold bypass;
  - the sandbox proxy blocking npm.

  Theme 3.

## Open questions for the course correction

- What is the deterministic definition of "flaky", and what does the runner do with a test that meets it (quarantine, ignore with an expiry, keep alerting)?
- Which decisions are protected (never taken while the Maintainer is offline), and which may an agent take provisionally, recording them for later review? Is a provisional decision revertible, and by whom?
- What does the catch-up digest contain, and where does it live (the inbox from Story 4.2, or a new summary)?
- How does a "failure that may matter later" get tracked, so the first downstream unit that depends on it is warned, or made to wait?
- Where do cross-project lessons live (Xarabot's package, a shared lessons file, or `brownfield-xaravel.md` § Lessons), and who promotes a per-repo lesson to a general one?
- Does any of this cut against SPEC's every-path approval until Epic 3, CAP-9's no-per-item-notice rule, or AGENTS.md's "stop and ask the Maintainer"?
